# 版本规则与发布流程

本文件是「今天摸了吗」**唯一的版本规则来源**。规则自 `v1.0.0` 起生效；
在它建立之前项目只有 `core.APP_VERSION = "1.0.0"`，没有版本递增规则，也没有更新记录，
因此按「如暂无版本规则，则从初始版本开始」定为 **`v1.0.0` 初始基线**。

## 一、版本号规则（语义化版本 SemVer）

格式：`MAJOR.MINOR.PATCH`，例如 `1.0.0`；预发布用 `-rc.1`，正式版不带后缀。

| 位 | 何时递增 | 本项目示例 |
| --- | --- | --- |
| `PATCH` | 缺陷修复、文档/构建脚本修正、不改变既有行为的小调整 | `1.0.0 → 1.0.1`：修复某个折算边界、修正 README 笔误 |
| `MINOR` | 新增功能、新增交付形式/平台、界面与交互增强、配置项新增（向后兼容） | `1.0.0 → 1.1.0`：新增导出报表、新增主题、新增一键安装包 |
| `MAJOR` | 配置格式或算法语义不兼容、接口/数据迁移需要人工介入、架构重写 | `1.0.0 → 2.0.0`：`config.json` 字段改名且不再兼容旧文件 |

补充约定：

- 一次提交只对应**一个**版本号；一个版本号可以包含多个变更，但必须全部写进同一条更新记录。
- 版本号必须与 git 附注标签 `vX.Y.Z` **一一对应**，不允许存在没有 CHANGELOG 条目的版本，也不允许存在没有标签的版本。
- 仅修文档/注释可不发版（标 `docs:` 提交），但**只要 `core.APP_VERSION` 变化就必须发版**。

## 二、版本号必须同步的位置

| 文件 | 字段 | 说明 |
| --- | --- | --- |
| `core.py` | `APP_VERSION` | 运行时唯一真值，主窗口页脚读取它 |
| `CHANGELOG.md` | 最新版本标题 `## [X.Y.Z] - YYYY-MM-DD` | 更新记录 |
| `README.md` | 顶部「当前版本」行 | 项目概述 |
| git tag | `vX.Y.Z` | 附注标签，指向该版本的发布提交 |

用 `python3 scripts/bump_version.py patch|minor|major` 自动同步前三处，
该脚本会校验「CHANGELOG 最新版本 == core.APP_VERSION == README 当前版本」，
并在版本不一致或 CHANGELOG 缺少对应条目时直接报错退出。

## 三、每次更新必须完成的 5 步

1. **递增版本**：`python3 scripts/bump_version.py <patch|minor|major> --date YYYY-MM-DD`
   脚本会在 `CHANGELOG.md` 顶部插入一条带完整字段的草稿。
2. **写全更新记录**：把草稿里的 `<请填写>` 全部替换。每条记录**必须**包含以下 6 个字段：

   | 字段 | 要求 |
   | --- | --- |
   | 变更目的 | 为什么改，解决什么问题 / 满足什么需求 |
   | 新增内容 | 新增的文件、功能、接口、配置项、交付物 |
   | 修复内容 | 修复的缺陷、根因、可复现场景 |
   | 调整内容 | 行为/界面/依赖/文档的调整，注明是否向后兼容 |
   | 影响范围 | 受影响模块、配置文件字段、平台、是否需用户操作 |
   | 已知问题 | 本次未解决或新引入的限制，没有也要写「无」 |

   并在条目标题写明 `对应版本：vX.Y.Z` 与 `对应提交：<说明>`。
3. **校验**：`python3 scripts/bump_version.py --check`（版本号四处一致、CHANGELOG 字段齐全、tag 与版本对应）。
4. **提交**：提交说明使用下面第四节模板，且必须带 `[vX.Y.Z]` 前缀。
5. **打标签并推送**：
   ```bash
   git tag -a vX.Y.Z -m "vX.Y.Z: <一句话摘要>"
   git push origin main --follow-tags
   ```

## 四、提交说明规范

格式（Conventional Commits + 版本前缀）：

```
[vX.Y.Z] <type>(<scope>): <一句话摘要>

目的：<为什么改>
- 新增：<...>
- 修复：<...>
- 调整：<...>
- 影响范围：<...>
- 已知问题：<...>
Refs: CHANGELOG.md#vXYZ
```

- `type`：`feat` / `fix` / `refactor` / `docs` / `build` / `test` / `chore` / `release`
- `scope`：模块名，如 `core` / `ui-settings` / `widget` / `web` / `packaging` / `docs`
- 摘要用中文，≤ 50 字；正文每条一行，与 CHANGELOG 条目保持一致。
- 不发版的日常提交用普通格式（无版本前缀），例如 `docs(readme): 补充排障步骤`。
- **禁止**在提交说明、代码、文档中写入 token、密钥、服务器地址、本机绝对路径。

## 五、更新记录模板

```markdown
## [X.Y.Z] - YYYY-MM-DD

**对应版本**：vX.Y.Z　**对应提交**：`[vX.Y.Z] type(scope): 摘要`

### 变更目的
<为什么做这次改动>

### 新增内容
- <新增 1>

### 修复内容
- <修复 1：现象 → 根因 → 处理>

### 调整内容
- <调整 1；注明是否向后兼容>

### 影响范围
- 模块：<...>
- 配置：<新增/变更字段，是否兼容旧 config.json>
- 平台与交付物：<...>
- 用户需做的事：<无 / 具体步骤>

### 已知问题
- <无 / 逐条列出>
```

## 六、追溯方式

```bash
git log --oneline --decorate          # 版本标签与提交
git show v1.0.0                       # 某版本发布提交全文
git diff v1.0.0..v1.0.1 --stat         # 两版本之间的改动范围
python3 scripts/bump_version.py --check
```

CHANGELOG、tag、commit message 三者都记录同一个版本号，任意一处都能反查另外两处。
